# 고정 테스트 문서 품질 루브릭

## 채점 공식

각 지표를 0~4 수준으로 판정한다.

```text
지표 점수 = 지표 배점 × 수준 ÷ 4
원점수 = 지표 점수의 합계
최종 점수 = 치명 결함 상한을 적용한 원점수
```

소수점이 생기면 지표 점수는 소수 첫째 자리까지 유지하고 총점에서 반올림한다.

## 공통 수준 앵커

| 수준 | 의미 | 판정 기준 |
|---:|---|---|
| 4 | 우수 | 대표 사례와 경계 사례를 문서만으로 일관되게 판단하며 중요한 누락·모순이 없다 |
| 3 | 양호 | 일반 사례는 독립적으로 처리하지만 일부 경계에서 추가 판단이나 저장소 탐색이 필요하다 |
| 2 | 보통 | 방향은 맞지만 중요한 결정 정보가 여럿 빠져 팀원별 결과가 달라질 수 있다 |
| 1 | 미흡 | 일반론 위주이거나 오류·모호성이 커서 실무 결정을 안정적으로 지원하지 못한다 |
| 0 | 결함 | 핵심 내용이 없거나 문서대로 따르면 중대한 오작동·오분류가 발생한다 |

최고 수준은 단순히 결함을 찾지 못했다는 이유로 부여하지 않는다. 해당 지표의 충분성을 뒷받침하는 긍정적 증거가 있어야 한다.

## 지표와 배점

### 1. 목적과 독자 명확성 — 10점

사용 대상, 적용 시점, 문서 범위, 범위 밖 항목과 기대 결과가 명확한지 평가한다.

### 2. 분류 기준과 결정 재현성 — 20점

도구 이름이 아니라 실제로 통과하는 경계로 테스트를 구분하며, 복합·경계 사례도 서로 다른 독자가 같은 분류에 도달할 수 있는지 평가한다. 파일 단위 분류와 중복 검증 방지 기준도 포함한다.

### 3. 실행 가능성 — 15점

파일명, 위치, 실행 명령, 환경, setup과 필수 자원을 문서만으로 결정할 수 있고 실제 수집·실행 구성과 연결되는지 평가한다.

### 4. 프로젝트 적합성과 사실 정확성 — 15점

실제 아키텍처, 계층, 도구, 경로, 오류 계약, mock 경계와 일치하는지 평가한다. 계획 중인 구조는 현재 사실과 명확히 구분해야 한다.

### 5. 예제와 검증 품질 — 15점

예제가 현실적이고 문법적으로 완결되며 올바른 assertion, 사용자 상호작용, mock 경계, 실패 의미를 보여주는지 평가한다. Good/Bad 예제가 이유까지 전달하는지도 본다.

### 6. 내부 일관성과 비모순성 — 10점

문서 간 용어, taxonomy, 명명, 위치, 책임과 예제가 충돌하지 않고 한 개념이 같은 의미로 사용되는지 평가한다.

### 7. 유지보수성과 단일 소스 — 10점

규칙과 설정의 소유권, 기준 문서, 링크, 변경 시 동기화 지점, 중복 최소화가 명확한지 평가한다. 특정 버전이나 구현을 복제했다면 변경 위험을 설명해야 한다.

### 8. 가독성과 탐색성 — 5점

정보 구조, 제목, 표, 링크, 용어 설명과 중복 수준을 평가한다. 문체 취향이나 한영 혼용만으로 감점하지 말고 검색·이해에 실제 영향을 줄 때만 감점한다.

## 치명 결함 게이트와 상한

아래 결함은 해당 지표에서 감점한 뒤 최종 점수 상한도 적용한다. 같은 원인을 별도 벌점으로 다시 빼지 않는다.

| 코드 | 치명 결함 | 최종 점수 상한 |
|---|---|---:|
| G1 | 문서대로 만든 테스트가 기본 CI 또는 명시된 실행 명령에 수집되지 않음 | 69 |
| G2 | 같은 규칙의 문서들이 파일 분류·위치·mock 경계를 서로 다르게 요구함 | 74 |
| G3 | Unit 테스트가 운영 DB, 실제 결제, 외부 네트워크 같은 비격리 자원에 접근하도록 요구함 | 49 |
| G4 | 테스트 간 상태 공유나 실행 순서 의존을 정상 전략으로 요구함 | 49 |
| G5 | 존재하지 않는 명령·계층·경로를 현재 표준으로 제시하여 일반 작업을 수행할 수 없음 | 59 |

여러 게이트가 해당하면 가장 낮은 상한을 적용한다. 향후 변경을 전제로 평가하라는 명시적 요청이 있으면 그 변경 범위와 직접 관련된 게이트만 유예하되 보고서에 반드시 밝힌다.

## 승인 등급

| 점수 | 등급 | 상태 |
|---:|---|---|
| 90–100 | A | 승인 가능 |
| 80–89 | B | 경미한 보완 후 승인 가능 |
| 70–79 | C | 운영 전 주요 수정 필요 |
| 60–69 | D | 표준 문서로 승인 불가 |
| 0–59 | F | 사용 위험, 전면 보완 필요 |

치명 결함 게이트가 하나라도 활성화되면 점수와 관계없이 승인 불가다.

## 대표 시나리오 검증

프로젝트에 존재하는 사례를 우선 사용한다. 사례가 없다면 아래 유형 중 최소 8개를 적용한다.

1. 순수 계산 또는 변환 함수
2. 입력 schema 검증
3. Server Action의 입력 변환과 service 위임
4. Service와 실제 데이터베이스 연결
5. Route Handler의 HTTP status 또는 envelope
6. 사용자 입력 후 UI 상태 변경
7. Hook → 데이터 클라이언트 → mock server 연결
8. 여러 컴포넌트가 로컬 UI 상태를 거치는 흐름
9. 실제 브라우저의 인증·권한 사용자 여정
10. 외부 결제·메일·스토리지를 mock한 내부 workflow

각 사례에서 다음 여섯 결정을 문서만으로 내릴 수 있는지 확인한다.

- 공개 테스트 분류
- 파일명
- 파일 위치
- 실제로 연결할 경계
- mock할 경계
- 실행 명령

각 결정은 `명확`, `추론 필요`, `결정 불가`, `문서 간 충돌` 중 하나로 표시한다. 전체 결정 중 `명확` 비율을 보고하되 이 비율을 총점에 별도로 더하지 않는다. 이는 2~4번 지표의 판정 증거다.

## 증거와 중복 감점 규칙

- 발견 사항마다 정확한 파일과 줄을 인용한다.
- 저장소 사실과 불일치를 주장할 때는 대응하는 설정 또는 제품 코드 근거도 인용한다.
- 하나의 근본 원인은 가장 직접적인 지표에서만 감점한다. 예를 들어 잘못된 파일 위치 때문에 CI에서 누락되는 문제는 실행 가능성에서 감점하고, 일관성 점수에서 다시 빼지 않는다.
- 사소한 오탈자는 의미나 검색성을 해칠 때만 가독성에서 묶어 한 번 감점한다.
- 증거 없이 미래 유지보수 위험을 단정하지 않는다.

## 반복 평가 비교

이전 보고서가 있더라도 이전 총점을 그대로 출발점으로 삼지 않는다. 현재 버전을 독립 채점한 후 비교한다.

각 기존 발견 사항을 다음 중 하나로 분류한다.

- 해결: 근거가 제거되고 대체 규칙이 명확함
- 부분 해결: 핵심 위험 일부만 남음
- 잔존: 실질적 변화 없음
- 회귀: 이전보다 영향이 커짐

새 문제는 `신규`로 구분한다. 점수 변화는 문구 수정량이 아니라 의사결정 가능성과 위험 변화로 설명한다.
