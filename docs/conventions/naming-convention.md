# 네이밍 컨벤션

> Last updated: 2026-09-21

프로젝트에서 사용하는 단어와 식별자 이름을 정할 때 적용하는 상위 기준이다. 이름의 케이스 자체보다 **표현하려는 역할과 의미를 먼저 판정**하고, 같은 의미에는 같은 단어를 사용한다.

## 적용 순서

이름을 새로 만들거나 기존 이름을 변경할 때 다음 순서로 판단한다.

1. 프레임워크·라이브러리·외부 프로토콜이 요구하는 이름인지 확인한다.
2. 프로젝트에서 이미 정한 용어가 있는지 확인한다.
3. 값·컴포넌트·타입·파일·폴더 중 어떤 역할인지 판정한다.
4. 역할에 맞는 케이스와 접미사를 적용한다.
5. 소비자가 이름만 보고 범위와 의미를 알 수 있는지 확인한다.

기존 코드의 이름을 바꿀 때는 참조처, 테스트, 외부 계약을 함께 확인한다. 단순히 문자열이 비슷하다는 이유로 의미가 다른 이름을 합치지 않는다.

## 우선순위와 예외

### 외부 이름은 경계에서 보존한다

Next.js·React·Radix·shadcn·SDK·Webhook·DB·프로토콜이 이름을 인식하거나 계약으로 고정한 경우 원형을 유지한다.

- `next/navigation`
- `NavigationMenu`, `NavigationMenuItem`
- Route Handler의 `GET`, `POST`
- 외부 API의 `snake_case` 응답 키

외부 이름을 프로젝트 내부 모델이나 함수명으로 전파하지 않는다. 필요한 경우 경계 DTO에서 내부의 프로젝트 용어로 변환한다. 외부 이름과 비슷하다는 이유로 프로젝트 소유 식별자까지 같은 예외를 적용하지 않는다.

### 기존 세부 규칙과의 관계

- 식별자 케이스·상수 판정: [식별자 명명 규칙](identifier-naming.md)
- URL 세그먼트·라우트 폴더: [라우트 명명 규칙](route-naming.md)
- 타입 import/export: [타입 import 규칙](type-imports.md)
- 하위 `AGENTS.md`에 더 구체적인 규칙이 있으면 해당 규칙을 우선한다.

## 단어 선택

### 같은 의미에는 하나의 정규형을 사용한다

동일한 개념을 축약형·전체형·유의어로 섞지 않는다. 새 이름은 기존 소비처에서 가장 넓게 통용되는 정규형을 선택하고, 정규형을 정하면 이후 이름에도 재사용한다.

예를 들어 사이트 메뉴를 뜻하는 정규형을 `Navigation`으로 정했다면 같은 의미의 프로젝트 소유 이름에서 `Nav`를 새로 만들지 않는다. 반대로 `Nav`를 정규형으로 채택하기로 결정했다면 `Navigation`과 혼용하지 않는다. 이 문서가 정규형을 자동으로 결정하지는 않으며, 도메인별 용어 표에서 선택한 정규형을 기록한다.

### 축약어는 어휘화된 경우만 사용한다

비개발자도 하나의 단어로 인식할 정도로 굳어진 약어만 허용한다. 그 외에는 전체 단어를 쓴다.

- 허용 예: `id`, `api`, `url`
- 지양 예: `addr`, `qty`, `pw`, 프로젝트 내부 임의 축약어

케이스별 표기는 [식별자 명명 규칙](identifier-naming.md)의 약어 규칙을 따른다(`ApiResponse`, `userId`, `API_BASE_URL`).

### 동사와 명사를 구분한다

- 데이터·컴포넌트·타입은 명사 또는 명사구로 짓는다.
- 함수·이벤트 핸들러·명령은 동사로 짓는다.
- `navigate`처럼 행위를 나타내는 단어를 목록·설정 데이터의 이름에 사용하지 않는다.
- `Navigation`은 이동 UI나 이동 개념, `navigate`는 이동을 수행하는 동작으로 구분한다.

## 컬렉션과 구성 요소

컬렉션의 모양과 화면에서의 역할을 이름에 반영한다.

| 표현       | 사용 기준                                     | 예시                          |
| ---------- | --------------------------------------------- | ----------------------------- |
| `Item`     | 컬렉션의 단일 구성 요소 타입·컴포넌트         | `OrderItem`, `BreadcrumbItem` |
| `items`    | 런타임에 전달·계산되는 구성 요소 배열         | `visibleItems`, `menuItems`   |
| `List`     | 여러 항목을 렌더링하는 UI 또는 목록 조회 결과 | `OrderList`, `ProductList`    |
| `links`    | 이동을 위한 링크 배열                         | `navigationLinks`             |
| `options`  | 선택 UI에 제공하는 선택지 배열                | `paymentOptions`              |
| `groups`   | 항목을 묶은 계층 단위                         | `navigationGroups`            |
| `sections` | 화면 또는 문서의 독립된 구획                  | `contentSections`             |
| `map`      | 키로 값을 조회하는 자료구조                   | `categoryLabelMap`            |

`List`를 단순 배열 변수의 의미로 사용하지 않는다. 반대로 화면 목록을 `items`라는 컴포넌트명으로 숨기지 않는다. 단, 외부 라이브러리 컴포넌트가 정한 이름은 보존한다.

### 복수형과 단수형

- 단일 엔티티·단일 구성 요소는 단수형을 사용한다.
- 여러 엔티티·구성 요소를 담는 값은 복수형을 사용한다.
- 컬렉션을 감싼 화면 컴포넌트는 역할에 따라 `*List`, `*Group`, `*Section` 중 하나를 선택한다.
- 하나의 배열이 여러 역할을 겸한다면 소비처별 별칭을 만들기보다 원본 데이터의 실제 역할을 명확히 한다.

## UI 이름

### 컴포넌트

컴포넌트명은 사용자에게 보이는 역할과 책임을 표현한다.

- 한 종류의 UI 동작을 제공하는 프리미티브는 표현 대상 중심으로 짓는다.
- 여러 항목을 표시하면 `*List`, 항목을 묶으면 `*Group`, 화면 구획이면 `*Section`을 사용한다.
- 구현 방식(`Wrapper`, `Container`, `Component`)을 의미 없이 붙이지 않는다.
- 공용 컴포넌트는 특정 라우트나 소비자 이름을 포함하지 않는다.

### props와 이벤트

- 외부에서 주입받는 콜백 prop은 `on` + 동작명으로 짓는다(`onSelect`, `onNavigate`).
- 컴포넌트 내부에서 이벤트를 처리하는 함수는 `handle` + 동작명으로 짓는다(`handleSelect`).
- 불리언은 `is`, `has`, `can`, `should` 중 의미에 맞는 접두사를 사용한다.
- 배열 prop은 배열의 역할을 드러내는 복수형을 사용한다(`items`, `links`, `options`).

## 파일과 폴더

파일·폴더 이름은 심볼의 역할과 디렉터리 규칙을 함께 따른다.

- `src/core/` 파일은 kebab-case를 사용한다.
- `src/ui/components/atoms/`의 flat 파일은 기존 atom·shadcn 규칙을 따른다.
- `molecules/`, `organisms/`, `templates/`는 컴포넌트 이름의 디렉터리와 파일 이름을 맞춘다.
- 라우트 세그먼트는 [라우트 명명 규칙](route-naming.md)을 따른다.
- 훅 파일은 export 심볼의 `useX`와 해당 폴더의 기존 파일명 규칙을 따르며, `use-`·`use_` 표기를 임의로 섞지 않는다.
- 같은 아티팩트 타입 사이에서 파일명 케이스를 혼용하지 않는다.

## 정규형 용어 기록

도메인에서 여러 표현이 발견되면 코드 변경 전에 아래 표에 정규형을 기록한다. 표에 없는 새 개념은 기존 개념과의 관계를 먼저 확인한 뒤 추가한다.

| 개념                  | 정규형                                        | 의미                                                                    | 혼용하지 않는 표현                       | 비고                                             |
| --------------------- | --------------------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------- | ------------------------------------------------ |
| 사이트 이동 UI·도메인 | `Navigation`                                  | 헤더·사이드바 등 사이트 내 이동과 그 구성을 나타내는 프로젝트 소유 이름 | `Nav`, `Navigate`                        | 지도 이동 UI·동작과 구분한다                     |
| 이동 항목             | `NavigationItem` 또는 역할이 드러나는 `*Link` | 이동 목록의 단일 항목 또는 링크                                         | `NavItem`, `NavigationLinkItem`          | 단순 데이터 항목은 `Item` 규칙을 따른다          |
| 단일 컬렉션 구성 요소 | `Item`                                        | 목록·그룹의 한 항목                                                     | `ListItem`을 일반 이름으로 사용하지 않음 | 외부 라이브러리가 요구하는 `*Item`은 원형 보존   |
| 렌더링 목록           | `List`                                        | 여러 항목을 표시하는 UI 또는 목록 조회 결과                             | `Items`를 컴포넌트명으로 사용하지 않음   | 단순 배열 변수는 `items` 등 역할별 복수형을 사용 |
| 계층형 항목 묶음      | `Group`                                       | 관련 항목을 묶은 UI·데이터 계층                                         | `Section`과 혼용하지 않음                | 메뉴 분류·필터 묶음 등에 적용                    |
| 독립 화면 구획        | `Section`                                     | 제목·콘텐츠·간격을 가진 화면의 독립 구획                                | `Group`과 혼용하지 않음                  | 페이지 구성 단위에 적용                          |

외부 라이브러리·프레임워크가 제공하는 `NavigationMenu`, `NavigationMenuList`, `NavigationMenuItem`, `List`, `Item` 등의 이름은 이 표의 프로젝트 소유 이름으로 치환하지 않는다. 이름을 새로 만드는 프로젝트 코드에서만 위 정규형을 적용한다.

정규형을 결정한 뒤에는 정의·구현·테스트·문서에서 같은 의미의 이름을 함께 갱신한다. 과거 작업 기록이나 외부 명칭은 변경 대상과 분리한다.

## 변경 절차

1. 정규형과 적용 범위를 이 문서의 용어 표에 기록한다.
2. 프로젝트 소유 코드와 외부 계약 코드를 구분한다.
3. 정의부와 모든 소비처·테스트를 함께 변경한다.
4. `lint`, `tsc`, 관련 테스트로 참조 누락과 의미 변경을 확인한다.
5. 다른 영역에서 발견한 별도 용어 혼용은 현재 변경에 끼워 넣지 말고 후속 작업으로 기록한다.
