# ADR-0003: 주문 기반 청첩장 도메인 모델

- 상태: Accepted
- 결정일: 2026-08-19
- 적용 범위: `src/models/`, `src/app/(preview)/`, `src/app/(main)/(my-order)/`, `src/app/api/guestbook/`

## 맥락

청첩장 콘텐츠를 담는 `CoupleInfo`는 `userId`만 참조하고, 주문과의 연결은 `Order.coupleInfoId`에 optional·non-unique로 걸려 있었다. 사용자가 청첩장을 두 건 구매하면 어느 콘텐츠가 어느 주문의 것인지 콘텐츠 쪽에서 판별할 수 없고, 여러 주문이 한 콘텐츠를 가리켜도 스키마가 막지 않았다.

공개 경로는 인증 없이 MongoDB ObjectId를 URL 키로 사용했다. ObjectId는 타임스탬프·프로세스 랜덤·카운터의 조합이라 암호학적 난수가 아니며, 같은 프로세스에서 생성된 문서끼리 상당 부분이 겹친다. 이 경로가 렌더하는 화면에는 신랑·신부 계좌번호와 혼주 연락처가 포함되고, 홈페이지가 샘플 청첩장의 id를 상시 노출해 추측의 출발점을 제공했다.

콘텐츠에는 발행 상태와 만료 개념이 없었다. 입력 도중인 청첩장과 완성된 청첩장이 구분되지 않았고, 예식이 끝난 뒤에도 계좌 정보가 무기한 공개된 채로 남았다.

## 결정

청첩장을 주문에 종속된 콘텐츠가 아니라 자체 정체성을 가진 엔티티로 둔다. 주문은 불변 상거래 기록이고 청첩장은 예식 전까지 계속 바뀌는 문서이므로, 두 생명주기를 하나의 식별자로 묶지 않는다. `orderId`는 "이 청첩장을 만든 주문"이 아니라 "현재 이 청첩장을 활성화한 주문"을 뜻하며, 템플릿을 교체해도 청첩장의 정체성과 그에 달린 방명록·배포된 링크는 유지된다.

식별자를 세 층으로 분리하고, 각 층의 노출 범위를 불변식으로 고정한다.

```text
Order._id           상거래 식별자        공개하지 않는다
Invitation._id      내부 콘텐츠 식별자    공개하지 않는다
Invitation.publicKey 암호학적 난수        하객에게 주는 유일한 값
```

공개 경로는 세션을 읽지 않는다. 이 불변식이 정적 렌더링을 가능하게 하는 동시에, 개인화된 내용이 공유 캐시에 섞이는 경로를 원천적으로 없앤다. 소유자만 볼 수 있어야 하는 화면은 공개 경로에 조건을 더하지 않고 인증이 걸린 별도 경로로 분리한다.

발행은 시스템이 추론하지 않고 소유자가 일으킨다. 필수 입력이 충족됐다는 사실이 "공개해도 좋다"를 뜻하지 않기 때문이다. 반대로 만료는 소유자의 행동이 아니라 시간의 함수이므로 상태로 저장하지 않고 예식일로부터 계산한다. 저장된 상태와 실제 시간이 어긋날 여지를 만들지 않는다.

## 검토한 대안

### 청첩장을 주문에 종속시키기

주문 하나에 청첩장 하나라는 관계를 가장 단순하게 표현한다. 그러나 청첩장의 정체성이 주문에 묶여 템플릿 교체가 곧 새 문서가 되고, 그 시점에 방명록과 이미 배포된 링크가 끊긴다.

### ObjectId를 공개 키로 유지하기

추가 필드 없이 기존 구조를 그대로 쓸 수 있다. 그러나 ObjectId는 추측 저항을 목적으로 만들어진 값이 아니어서, 계좌번호와 연락처가 담긴 화면의 유일한 접근 통제로 쓸 수 없다.

### 만료를 상태로 저장하고 배치로 전환하기

만료 여부를 질의로 직접 필터링할 수 있다. 그러나 스케줄러라는 새 인프라가 필요하고, 배치 지연 시 만료됐어야 할 청첩장이 살아 있으며, 예식 연기를 상태 되돌림 로직으로 따로 처리해야 한다.

### 공개 경로에서 세션을 보고 분기하기

라우트를 추가하지 않고 소유자 미리보기를 제공한다. 그러나 쿠키를 읽는 순간 해당 경로 전체가 동적으로 전환되어, 하객이 보는 화면까지 매 요청 렌더된다.

## 결과

주문과 청첩장의 1:1 관계가 스키마로 강제되고, "아직 입력하지 않음"이 null 필드가 아니라 문서의 부재로 표현된다. 상거래 식별자가 공개 표면에서 완전히 빠지므로 하객이 유효한 주문 식별자를 알게 되는 경로가 사라진다. 링크 재발급이 공개 키 재생성만으로 가능해지고, 공개 경로가 세션을 읽지 않는다는 불변식 덕분에 정적 렌더링과 접근 통제가 서로를 방해하지 않는다.

대가로 청첩장 엔티티에 필드가 늘고, 주문 목록이 청첩장 상태를 알기 위해 질의를 한 번 더 수행한다. 소유자 미리보기가 별도 경로로 분리되면서 라우트도 하나 늘어난다. 발행 조건을 따로 두지 않기로 해 이미지나 계좌가 비어 있어도 발행이 가능하며, 이 판단은 시스템이 아니라 고객이 경고를 보고 내린다.

잔여 위험은 두 가지다. 공개 키가 유출되면 그 청첩장은 노출되며, 이는 키 재발급으로만 회수할 수 있다. 그리고 만료가 저장되지 않으므로 만료된 청첩장을 질의로 직접 걸러낼 수 없고, 예식일 범위 조건으로 대신해야 한다. 두 위험 모두 감수 가능한 수준으로 판단했으나, 커스텀 URL 슬러그를 판매하기로 결정하는 시점에는 첫 번째 위험의 전제가 바뀌므로 계좌 노출 정책을 함께 재검토해야 한다.
