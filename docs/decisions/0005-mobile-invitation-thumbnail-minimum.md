# ADR-0005: 모바일 청첩장 발행 최소 요건 — 썸네일 정확히 3장

- 상태: Accepted
- 결정일: 2026-09-04
- 적용 범위: `src/core/schemas/request/mobileInvitationContent.schema.ts`, `src/services/mobile-invitation.ts`

## 맥락

[ADR-0003](0003-order-scoped-invitation-model.md)은 "필수 입력이 충족됐다는 사실이 공개해도 좋다를 뜻하지 않는다"는 원칙 아래 발행 최소 요건을 시스템이 아니라 고객의 판단에 맡기기로 했고, 그 결과 "이미지·계좌가 비어 있어도 발행 가능"이라 명시했다.

실제 구현은 이 결정과 어긋나 있었다. 서버 검증 스키마(`coupleInfoSchema`)엔 썸네일 개수 제약이 아예 없었고, 클라이언트 전용 스키마(`coupleInfoClientSchema`)만 최소 1장을 요구했다 — 같은 도메인 규칙이 두 곳에 다르게 박혀 있어 클라이언트를 우회하면 0장짜리 청첩장도 저장·발행될 수 있었다. 한편 UI(`ImagesSection.tsx`)는 처음부터 "메인 이미지(3장)"라는 문구와 `maxCount={3}`으로 3장을 전제하고 있어, 실제 운영 의도는 애초에 "정확히 3장"이었다는 것이 드러났다.

## 결정

썸네일 이미지는 정확히 3장을 발행 최소 요건으로 못박는다. 이 요건은 서버 스키마 하나에만 정의하고 클라이언트는 같은 스키마를 그대로 재사용한다 — 서버와 클라이언트가 서로 다른 규칙을 갖는 이중 스키마 구조를 두지 않는다. 계좌 정보 등 그 외 필드의 "비어 있어도 발행 가능"이라는 ADR-0003의 원칙은 그대로 유지한다 — 이번 결정은 썸네일 개수 요건 하나만 다룬다.

## 검토한 대안

### 서버 검증 없이 클라이언트 검증만 강화

변경 범위가 작다. 그러나 Server Action은 클라이언트를 거치지 않고도 직접 호출 가능한 공개 진입점이라 우회 저장을 막지 못한다.

### 최소 1장 유지, UI 문구만 스키마에 맞춰 수정

기존 코드 변경이 없다. 그러나 UI가 이미 3장을 전제로 슬롯을 고정해 둔 상태라, 문구를 스키마에 맞추면 오히려 실제 업로드 UX(3칸 고정)와 검증 규칙이 다시 어긋난다.

## 결과

서버·클라이언트가 하나의 스키마(`mobileInvitationContentSchema`)를 공유해 우회 저장 경로가 없어졌고, 검증 규칙과 UI 문구·업로드 슬롯 수가 일치한다. 트레이드오프로 클라이언트 전용 스키마 분리가 주던 유연성(클라이언트만 더 엄격하게 가져가는 점진적 롤아웃 등)은 없앴다 — 현재 이 기능에 그런 롤아웃 요구가 없어 감수 가능하다고 판단했다.
