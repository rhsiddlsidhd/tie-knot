# ADR-0004: 배럴 없는 명시적 모듈 경로

- 상태: Accepted
- 결정일: 2026-09-02
- 적용 범위: `src/`

## 맥락

`src/` 하위는 폴더마다 `index.ts` 배럴을 두고 그 배럴로만 import하는 것을 컨벤션으로 삼아 왔다. 배럴은 예외 없이 `export * from "./x"`로만 구성했고, 그 결과 `@/` 경로 import 1070건 중 992건(93%)이 배럴을 거친다. 배럴 파일은 81개다.

Vite와 Vitest의 모듈 그래프는 심볼이 아니라 모듈 단위로 계산된다. 배럴에서 심볼 하나만 가져와도 배럴 파일이 평가되면서 `export *` 대상 전부가 그래프에 들어오고, 그 모듈들이 다시 배럴을 물면 의존이 연쇄로 전파된다. 트리셰이킹은 프로덕션 번들러의 최적화이므로 이 경로에는 적용되지 않는다. 측정 결과 `vitest related src/actions/logoutUser.ts`는 154개 중 93개 테스트 파일을 실행하며 145.5초가 걸린 반면, 어떤 배럴에도 실리지 않은 `src/proxy.ts`는 1개, 0.31초였다. 466배 차이의 유일한 변수는 배럴이다. 이 때문에 `vitest related`, `vitest --changed`, watch 모드가 이 저장소에서 실질적으로 쓰이지 못하며, 같은 모듈 그래프를 사용하는 mutation testing 도구도 도입 시 동일한 증폭을 받는다.

정적 그래프 분석을 실측 3회로 교정해 검증한 뒤 조합을 탐색한 결과, 비용은 균일하지 않았다. `actions` → `services` → `models` 세 배럴을 함께 끊으면 위 수치가 93에서 6으로 떨어지지만, 셋 중 하나라도 남기면 나머지를 끊어도 93에서 내려가지 않는다. 반면 최다 사용처인 `@/core/domain`(371건)을 포함해 `atoms`(139건), `core/utils`(115건)를 끊는 것은 효과가 정확히 0이다. 즉 "무해한 배럴"과 "유해한 배럴"이 갈리지만, 그 분류는 측정 시점의 스냅샷이다. 실제로 `core/domain`은 ADR 작성 직전까지 날짜 연산 함수를 품고 있었고(#207) 그 사실을 아무도 인지하지 못했다.

## 결정

`src/` 안에서는 배럴을 두지 않는다. import는 항상 심볼이 실제로 정의된 파일을 지정한다.

```text
import { logoutService } from "@/services";        →  금지
import { logoutService } from "@/services/auth";   →  기준
```

이 규칙은 성능이 아니라 **검사 가능성**을 위해 전면 적용한다. 성능 이득은 세 배럴을 끊는 121개 파일에서 나오고 나머지는 측정상 이득이 없지만, 규칙을 "어떤 폴더는 배럴을 둬도 된다"로 나누는 순간 판정 기준이 사람의 재분류에 의존하게 된다. 어떤 레이어가 아직 순수한지는 시간이 지나면 조용히 거짓이 되고, 그것을 지켜보는 주체는 없다. 경계가 하나뿐인 규칙만이 도구로 강제된다.

폴더의 공개 API를 배럴로 선언하던 역할은 사라진다. 무엇이 외부에서 쓰여도 되는지는 재수출 목록이 아니라 각 계층의 `AGENTS.md`가 규정하는 역할 경계로 판단한다. 이는 ADR-0001이 세운 역할 기반 디렉터리 구조를 그대로 따르며, 배럴은 그 경계를 표현하는 여러 수단 중 하나였을 뿐이다.

Next.js가 파일 규약으로 강제하는 `src/app/` 라우트 파일은 이 결정의 적용 대상이 아니다. 그 폴더는 파일 경로 자체가 라우팅 키이므로 애초에 배럴로 재수출해도 동작하지 않는다.

## 검토한 대안

### 현행 유지

배럴은 폴더의 공개 API를 한곳에 선언하고 내부 파일 구조 변경을 외부로부터 감춘다. 그러나 이 이점의 대가로 `related`·`--changed`·watch·mutation 도구 전체를 포기하게 되며, 측정된 466배 차이는 개발 루프에서 회복되지 않는다.

### 역할 계층 기준 부분 제거

서버 실행 경로(`actions`·`services`·`models`)에만 배럴을 금지하면 121개 파일 수정으로 측정된 이득 전부를 얻는다. 그러나 나머지 폴더가 "무해하다"는 판정이 측정 시점에 묶여 있고, 순수 레이어에 무거운 의존이 섞여 들어와도 아무도 재측정하지 않는다. 규칙이 기계 검사에서 사람 판단으로 내려간다.

### 값과 타입 기준 분리

배럴이 타입만 재수출하게 하면 단일 규칙을 유지하면서 런타임 그래프를 정리할 수 있다. 그러나 `routes`처럼 무해한 상수까지 deep import 대상이 되어 비용은 크게 줄지 않으면서, "이 심볼이 타입인가 값인가"라는 판정이 모든 import 지점에 새로 생긴다.

## 결과

`vitest related`와 `--changed`가 실제 영향 범위만 실행하게 되어 watch 루프가 회복되고, mutation testing 도입의 선행 조건이 해소된다. 모듈 그래프가 실제 의존을 반영하므로 클라이언트 번들에 서버 모듈이 딸려 들어가는 경로도 import 구문에서 드러난다. 규칙은 "디렉터리를 가리키는 import 금지"와 "`src/` 안 `index.ts` 금지"라는 두 조건으로 환원되어 lint로 검사할 수 있다.

대가로 992건의 import 구문을 수정해야 하고, 그중 871건은 측정 가능한 성능 이득이 없다. 여러 심볼을 한 줄로 가져오던 자리는 파일별로 나뉘어 import 구문 수가 늘어난다. 파일을 옮기면 사용처를 모두 갱신해야 하지만 이는 IDE의 기계적 처리 범위 안에 있다.

남는 위험은 폴더 내부 전용으로만 쓰이던 파일이 외부에서 직접 import될 수 있다는 점이다. 배럴이 담당하던 차단은 사라지므로, 무엇을 외부에 노출하는지는 각 계층 `AGENTS.md`의 역할 규정과 코드 리뷰가 가드한다. 마이그레이션 자체는 배럴 하나를 완결해야 효과가 나타나므로, 중간 상태에서는 측정으로 진척을 확인할 수 없다는 점도 감수한다.
